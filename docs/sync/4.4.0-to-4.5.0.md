# Upstream diff: h3-4.4.0 -> h3-4.5.0 — discovery record

**Status: discovery only.** This record accounts for every change between
the two upstream tags and assigns each an explicit disposition. No
production migration has been performed: the repository's H3 Core
behavioral target and parity oracle remain **v4.4.0** throughout this
record, and every disposition marked *to-port* names the implementation
issue (§15) that will carry it out. Discovery scope and acceptance
criteria: [issue #25](https://github.com/dimchansky/h3-go/issues/25).

Disposition vocabulary (issue #25): **to-port** (ported in a named later
implementation issue) · **already-equivalent** (with evidence) ·
**test-only** · **documentation-only** · **tooling/build/infrastructure-only**
· **n/a** (not applicable to this pure-Go port, with a concrete reason) ·
**decision** (requires a separate design or implementation decision).

## 3. Upstream release and PR overview

From the v4.5.0 release notes (overview only — §5 is derived from the
tag-to-tag diff, not from the notes):

- **Added**: internal `cellsToMultiPolygon` + `destroyGeoMultiPolygon`

  refactored onto Vec3d (#1145, #1155); CoordIJK made inlineable (#1154).
- **Fixed**: CLI handling of invalid cell input (#1125, #1124);
  `destroyLinkedMultiPolygon` idempotent (#1136).

## 4. Public API delta

The `h3api.h.in` diff between the tags contains exactly **one** new
public function and one comment reword:

- `DECLSPEC H3Error H3_EXPORT(reverseDirectedEdge)(H3Index edge, H3Index *out)`
  — "Returns the directed edge with origin and destination cells
  reversed". The only public-API signature addition in v4.5.0.
- The `cellsToLinkedMultiPolygon` brief changed from "…from a set of
  contiguous hexagons" to "…from a set of cells", and its `@defgroup`
  comment now reads "Functions for cellsToMultiPolygon (currently a
  binding-only concept)".

**Verified: `cellsToMultiPolygon` is not public in v4.5.0.** It is
`H3_EXPORT`ed for bindings but declared in the *internal* header
`cellsToMultiPoly.h`, whose comment states: "This definition is
tentative as we work to finish the implementation. TODO: This will be
moved to h3api.h.in when it is ready to release." The same applies to
`destroyGeoMultiPolygon`. Neither may become public Go API in this
migration (§13). `GeoMultiPolygon` itself is **not** new — the type
already exists verbatim in the 4.4.0 `h3api.h.in`.

`go run ./tools/apiinventory -h3ver 4.5.0 -verify` confirms: 79 public C
functions (was 78), 2 problems, both for `reverseDirectedEdge` (no port,
no `H3 C API:` reference). No public function was removed; no error
codes were added or removed (`describeH3Error` and the `H3_ERROR_END`
sentinel are unchanged).

### 5.2 Domain notes (verified against both trees)

**coordijk (56 move rows + 2 macro rows).** All 28 functions from the
4.4.0 `coordijk.c` reappear in the 4.5.0 `coordijk.h` as `static inline`
with **statement-identical bodies** (verified function-by-function;
only qualifiers, definition order, includes, and comment re-wrapping
differ). `CoordIJK`, `UNIT_VECS`, and the `Direction` enum are
byte-identical between the two headers. This is a pure
mechanical move; the 29 Go `coordijk__*.go` / `coordijk_*.go` bodies
need **no change** — only their `Ported from H3 C: coordijk.c::…`
attributions must be retargeted to `coordijk.h::…` so the sync tooling
keeps mapping (I-G; see §14 for the attribution-convention decision).

**vec3d.** `vec3d.c` is deleted; `vec3d.h` becomes header-only ("static
inline so callers in other translation units can inline these without
requiring LTO"). Mapping: `_geoToVec3d` → `latLngToVec3` (identical
math, pointer-out → by-value); `_pointSquareDist` → `vec3DistSq`
(rewritten via `vec3LinComb`+`vec3NormSq`, IEEE-754-equivalent —
multiplication by ±1.0 is exact and term order is unchanged); `_square`
removed with no successor. Genuinely new: `vec3ToLatLng`, `vec3LinComb`,
`vec3Cross`, `vec3Dot`, `vec3NormSq`, `vec3Norm`, `vec3Normalize`
(zero-norm guard). All ported in I-A; the three old Go files retire.

**faceijk / h3Index (Vec3 indexing refactor).** The old lat/lng
spherical-trig projection (`_geoToFaceIjk`/`_geoToHex2d`/`_faceIjkToGeo`/
`_hex2dToGeo`/`_geoToClosestFace`, azimuths via `_geoAzimuthRads`/
`_geoAzDistanceRads`) is replaced by a unit-vector pipeline
(`_vec3ToFaceIjk`/`_vec3ToHex2d`/`_faceIjkToVec3`/`_hex2dToVec3`/
`_vec3ToClosestFace`, azimuths via `_vec3AzimuthRads` over a
`_vec3TangentBasis`). The (r, θ) gnomonic math is byte-identical; only
the spherical-trig legs moved to vector algebra. `latLngToCell` and
`cellToLatLng` now delegate to new internal `vec3ToCell` / `cellToVec3`
(declared in `h3Index.h`); `vec3ToCell` returns `E_DOMAIN` (not
`E_LATLNG_DOMAIN`) for non-finite vector components. The two boundary
builders keep their structure but emit each vertex via
`_hex2dToVec3` + `vec3ToLatLng`; `_faceIjkPentToCellBoundary` also
zero-initializes a previously uninitialized local (`FaceIJK lastFijk = {0}`).
**Upstream makes no bit-identical claim** for the refactor; its own
tests stayed tolerance-based and unchanged. See §14 (risk 1).

**latLng.** Pure removals; no remaining body changed. `cellAreaRads2/
Km2/M2` moved to the new `area.c` *and were reimplemented*;
`triangleArea`/`triangleEdgeLengthsToArea` (the l'Huilier
spherical-excess path) and `_geoAzimuthRads`/`_geoAzDistanceRads` (only
callers were the removed faceijk legs) are deleted with no successors.

**area / adder (new).** `adder.h` is classic Kahan compensated summation
(`Adder{sum, _c}` + `kadd`; upstream chose Kahan over naive/Neumaier and
cites d3-geo). `area.c` computes loop area by summing the d3-geo-style
`cagnoli` per-edge spherical-excess term with Kahan compensation
(`geoLoopAreaRads2`, auto-closing, result normalized into [0, 4π];
reversed loops give `4π − a`), plus `geoPolygonAreaRads2` (holes
subtracted via the `+ hole − 4π` identity) and
`geoMultiPolygonAreaRads2`. `cellAreaRads2` becomes `cellToBoundary` →
`geoLoopAreaRads2` — a genuinely different algorithm from 4.4.0's
center-fan of triangles, with **different numeric results** (upstream
tightened its whole-earth sum tolerance to a uniform 1e-14 rads² at
res 0–4 and deleted the "drop in accuracy at resolution 1" comment).
Go caveat recorded for I-B: Kahan summation must not be algebraically
"simplified" during the port; Go's non-reassociating float64 semantics
preserve it as long as the four statements stay as written.

**cellsToMultiPoly (new).** Arc-cancellation multipolygon algorithm:
each cell contributes its 5–6 directed edges as `Arc`s in a per-cell CCW
doubly-linked loop (union-find component per cell) and an
open-addressing hash table (`hashEdge`, `HASH_TABLE_MULTIPLIER = 10`);
`cancelArcPairs` removes each edge whose `reverseDirectedEdge` is also
present, splicing loops and unioning components, so surviving arcs form
the boundary loops. Loops are extracted (`createSortableLoop`, vertices
from `directedEdgeToBoundary` minus each edge's last vertex, area via
`geoLoopAreaRads2`), sorted by (component root asc, area asc) — putting
each polygon's outer loop (smallest enclosed area) first and holes
after — grouped into `SortablePoly`s, and finally sorted by **outer-loop
area descending** (`cmp_SortablePoly`), which determines output polygon
order. If every edge cancels (input tiles the globe),
`createGlobeMultiPolygon` emits 8 fixed triangular octant polygons.
Note the internal `cellsToMultiPolygon` takes `int64_t numCells` (the
linked variant keeps `const int numHexes`). Depends on
`reverseDirectedEdge` (I-E) and `geoLoopAreaRads2` (I-B).

**algos / linkedGeo.** `cellsToLinkedMultiPolygon` is rewritten to
`cellsToMultiPolygon` → `geoMultiPolygonToLinkedGeoPolygon` →
`destroyGeoMultiPolygon` (no `normalizeMultiPolygon` call on this path
any more — output is normalized by construction; `normalizeMultiPolygon`
itself is body-unchanged, comment-only, §6). `h3SetToVertexGraph`,
`_vertexGraphToLinkedGeo`, and all of `vertexGraph.c/h` are deleted.
linkedGeo gains linked↔flat conversion helpers
(`linkedGeoPolygonToGeoMultiPolygon`, `geoMultiPolygonToLinkedGeoPolygon`
extern in `linkedGeo.h`; loop/polygon-level helpers static);
`countLinked*` changed only by `const` qualifiers (no behavior change);
`destroyLinkedMultiPolygon` now zeroes the caller-owned head node,
making a second call a no-op ("idempotent" — C memory-management
behavior; the Go linked structures are internal, DEVIATIONS §4).
`destroyGeoLoop`/`destroyGeoPolygon` live in `algos.c` (declared in
`polygon.h`); `destroyGeoMultiPolygon` is binding-only exported.

**localij (bidirectional gridPathCells).** The old single-pass body is
extracted into `gridPathCellsInterpolate(start, end, distance, out,
outOffset, outStep)` (fills forward or reverse in place). New
`gridPathCells`: `gridDistance` first (errors propagate unchanged); a
new `distance == 0` fast path (`out[0] = start`); a forward attempt
anchored at `start`; on failure a **retry anchored at `end`** writing the
reversed traversal; if both fail, the *forward* attempt's error is
returned. Paths that previously failed with `E_PENTAGON` can now
succeed; error codes are otherwise unchanged. `localIjkToCell` changed
comment-only; `gridDistance`, `cellToLocalIj`, `localIjToCell`,
`cellToLocalIjk` are untouched. (The new `#include "algos.h"` /
`"alloc.h"` in localij.c appear unused — noted in §14.)

**directedEdge.** One addition, `reverseDirectedEdge`:
`getDirectedEdgeOrigin` → `getDirectedEdgeDestination` →
`cellsToDirectedEdge(destination, origin, out)`, propagating the first
error. Validation is **partial** — mode check plus neighbor-rotation
checks, not full `isValidDirectedEdge` (upstream's own
`reverseDirectedEdgeInvalid` test documents that `edge + 1`, invalid per
`isValidDirectedEdge`, still succeeds). Observed error surface:
`E_DIR_EDGE_INVALID`, `E_PENTAGON`, `E_NOT_NEIGHBORS` (upstream's
`fuzz_fail` pin), plus propagated codes. Rest of the file is
byte-identical.

   4.5.0: "All cells must be valid, same resolution, no duplicates.
   Returns an error if these conditions are not met." Implementation
   (via `validateCellSet`): `numCells < 0` → `E_DOMAIN`; per-cell
   `isValidCell` → `E_CELL_INVALID` (checked before resolution, so an
   invalid cell reports `E_CELL_INVALID` even if it also mismatches);
   resolution vs `cells[0]` → `E_RES_MISMATCH`; sorted duplicate scan →
   `E_DUPLICATE_INPUT` (the release notes say `E_DOMAIN` for duplicates
   — **the notes are wrong; the tagged code returns
   `E_DUPLICATE_INPUT`**, and upstream's `duplicate_cells` test asserts
   exactly that). Empty input stays a success with empty output. The
   overflow pre-check can also surface `E_MEMORY_BOUNDS`. Upstream's
   `specificLeak` test changed its expectation from `E_FAILED` to
   `E_CELL_INVALID` accordingly. **Go impact (I-C)**: the
   `CellsToMultiPolygon` wrapper's documented "undefined output"
   becomes a guaranteed-error contract (issue #20/#15 policies decide
   the exact GoDoc wording; the error-classification is upfront and
   exhaustive, so these qualify as guaranteed errors).
2. **Multipolygon output ordering.** The new algorithm normalizes by
   construction: outer loops CCW, holes CW, holes after their outer
   loop; polygons ordered by outer-loop area **descending**; loop start
   vertex falls out of arc scan order. Observable consequence (verified
   by the CLI differential, §10): hole-loop vertex *rotation* differs
   from 4.4.0 for the same cycles. Upstream does not document loop
   start or polygon order as a contract — per the issue #15 ordering
   policy, the Go port must not promise them (I-C docs).
3. **`gridPathCells` reachability.** Pentagon-adjacent paths that
   previously failed `E_PENTAGON` can now succeed via the end-anchored
   retry; a `distance == 0` fast path writes the start cell. Path
   *contents* remain explicitly unstable across versions (upstream
   disclaimer retained). Upstream replaced its `gridPathCells_pentagon`
   failure test with `gridPathCells_pentagonReverseInterpolation`
   (success) and pinned one still-failing pair
   (`gridPathCells_knownFailureNotCoveredByReverseInterpolation`,
   0x8411b61ffffffff → 0x84016d3ffffffff).
4. **`cellAreaRads2/Km2/M2` numerics.** New algorithm (boundary loop
   area, Kahan-compensated) — same contract, different (more accurate)
   floating-point results. Upstream's per-cell km² expectations were
   loose enough to survive unchanged; the whole-earth sums tightened to
   1e-14 rads². Parity for these functions must be re-established
   against the 4.5.0 oracle, and h3-go's measurement GoDoc (issue #21)
   re-audited (I-B).
5. **`latLngToCell`/`cellToLatLng`/`cellToBoundary` numerics.** The Vec3
   refactor changes the floating-point operation sequence with no
   upstream bit-identical claim. §16 records that the 526,546-record
   golden fixture suites (tolerance-based where coordinates are
   compared) pass against the unchanged 4.5.0 fixture files; exact
   Go-vs-C parity at 4.5.0 is deferred to I-A after I-T (§14 risk 1).
6. **`reverseDirectedEdge` (new, public).** Partial validation (§5.2);
   error surface `E_DIR_EDGE_INVALID` / `E_PENTAGON` /
   `E_NOT_NEIGHBORS` / propagated. Issue #15 error policy: the invalid-
   edge behavior is a *precondition with best-effort detection*, not a
   guaranteed error (upstream's own test shows an invalid edge
   succeeding) — this classification constrains the I-F GoDoc.
7. **`destroyLinkedMultiPolygon` idempotence.** C memory-management
   behavior (head node zeroed). The Go ported function mirrors
   structure-zeroing for parity of the ported layer, but there is no
   public Go impact: linked-geo structures are internal and `destroy*`
   is not exposed (DEVIATIONS §4). Disposition: to-port in I-C at the
   ported layer; n/a at the public layer.
8. **CLI cell-input scanner.** The 1500-byte chunked reader now zeroes
   stale buffer bytes after a short `fread`; `edgeLengthM` prints
   `%.8lf` (was `%.10lf`); an "Unompacts" help typo is fixed. These
   change observable CLI outputs (§10) and the reproduced-bug contract
   in `docs/cli-compatibility.md` (I-H).

## 13. Public Go API design decisions

**13.1 `reverseDirectedEdge` — two decisions, kept separate.**

*Internal port (I-E, decided):* port the exact C function as an
unexported, C-traceable implementation named `reverseDirectedEdge` in
`directedEdge_reverseDirectedEdge.go`, preserving the C name, C-shaped
control flow, and the attribution
`// Ported from H3 C: directedEdge.c::reverseDirectedEdge`; add the cgo
wrapper against the exact v4.5.0 function and parity tests covering
upstream's success, double-reversal, invalid-edge, partial-validation,
and fuzz-regression (`0x1001fff7ff2fbfff` → `E_NOT_NEIGHBORS`) cases.
This is mechanical and not a design question.

*Public API (I-F, a design record to be written and approved in that
issue — NOT decided here).* Checklist the record must resolve, with the
discovery evidence attached:

- **Shape/name**: method `DirectedEdge.Reverse` vs package function.
  Evidence: the official binding chose `DirectedEdge.Reverse()` (§11);
  this repository puts single-receiver operations on the typed receiver
  (`DirectedEdge.Origin`, `.Destination`, `.Cells`, `.Boundary`), so a
  method is the natural fit — but the record decides.
- **Signature/errors**: `(DirectedEdge, error)` is the obvious
  candidate; the record must classify failure behavior per issue #15:
  invalid input is a *precondition with best-effort detection*
  (§7 item 6 — upstream's test shows an invalid edge succeeding), so
  GoDoc must not promise a guaranteed `ErrDirectedEdgeInvalid`; the
  sentinel families a caller must handle include `ErrDirectedEdgeInvalid`,
  `ErrPentagon`, `ErrNotNeighbors`.
- **Bounds/validation in the wrapper**: whether the Go wrapper
  pre-validates (cf. DEVIATIONS §6/§8 precedents) or mirrors C's
  partial checks exactly — mirroring is the default absent a registered
  deviation.
- **Allocation**: expected zero-allocation (pure bit manipulation +
  lookups); claim only with an allocation assertion.
- **Aliasing/lifetime**: value semantics, nothing to state.
- **`Append*`/`Seq` forms**: not meaningful (scalar in, scalar out).
- **Docs**: `H3 C API: reverseDirectedEdge` line; GoDoc from the C
  leading comment under issue #15/#21 policies.
- **Golden file/inventories**: `docs/api-surface.txt` regeneration,
  apiinventory row, ubercompare/api-map rows, `Example` test.
- **Compatibility**: pure addition; pre-v1 minor-version material
  (`../versioning.md`).

**13.2 `cellsToMultiPolygon` — no public Go API in this migration
(decided).** Verified binding-only/tentative upstream (§4). The internal

### 15.1 I-T: the selected dual-version harness mechanism

Today the harness has a single build dimension — every parity file is
constrained `//go:build cgo && c2go` — and `make test-c2go H3VER=<ver>`
varies **only the C include path** (`testref/h3-$(H3VER)/src/h3lib`).
That is insufficient for 4.5.0 because the tree *shape* changed:
`coordijk.c`/`vec3d.c`/`vertexGraph.c` and `vertexGraph.h` no longer
exist, and `area.c`/`cellsToMultiPoly.c` are new. Selected mechanism,
three parts:

1. **coordijk only: the C shim becomes tree-shape-adaptive via
   `__has_include`** (no Go build dimension needed for this domain,
   because the move is same-named). `h3lib_coordijk_c2go.c` is
   rewritten as
   `#if __has_include("coordijk.c") / #include "coordijk.c" / #endif`
   (supported by the clang/gcc toolchains the harness already
   requires). At 4.4.0 the shim compiles the implementation exactly as
   today; at 4.5.0 it compiles to an empty translation unit and the
   cgo bridge's existing preamble `#include "coordijk.h"` picks up the
   now-`static inline` definitions in the cgo-generated translation
   unit — every function keeps its 4.4.0 name and signature (§5.2),
   so calls through `C.<name>` resolve in both configurations and the
   existing coordijk wrappers need no change. **This mechanism does
   NOT extend to vec3d**: the vec3d change is not a same-name move —
   `_geoToVec3d`, `_pointSquareDist`, and `_square`, the symbols
   `vec3d_cgo.go` binds, do not exist under any name-compatible form
   at 4.5.0 (the successors are the renamed/by-value `latLngToVec3`,
   `vec3DistSq`, etc.). vec3d is therefore handled by the version
   build tag in part 2.
2. **A version build tag for everything version-specific at the Go
   level.** `make test-c2go` derives a tag from `H3VER` (e.g. `h3v450`
   when `H3VER=4.5.0`) and passes it via `-tags`. Files that reference
   symbols existing in only one tree are split by that tag — and
   because the Go toolchain compiles package C files automatically
   (the root `Makefile` never enumerates them), C shims are gated the
   same way: a `//go:build cgo && c2go && !h3v450` constraint line in
   the C file itself, exactly like the `//go:build cgo && c2go` line
   every shim already carries. Gated `!h3v450` (4.4.0-only; deleted at
   the I-I cutover):
   - `h3lib_vertexGraph_cgo.c` — the source-file build constraint is
     the single selected mechanism for this shim;
   - the `vertexGraph_cgo.go` wrappers and all
     `vertexGraph*_parity_test.go`;
   - the `h3SetToVertexGraph`/`_vertexGraphToLinkedGeo` wrapper+tests
     currently reachable through `algos_cgo.go`, whose preamble
     `#include "vertexGraph.h"` moves into the tag-gated file
     (clearing the §16 build blocker);
   - **the old vec3d harness**: `vec3d_cgo.go`, its parity tests
     (`vec3d__geoToVec3d_parity_test.go`,
     `vec3d__pointSquareDist_parity_test.go`,
     `vec3d__square_parity_test.go`), and the old C shim
     `h3lib_vec3d_c2go.c`;
   - the remaining old-pipeline faceijk/latLng parity tests as their
     domains migrate.
   Gated `h3v450` (new pieces): `h3lib_area_c2go.c`,
   `h3lib_cellsToMultiPoly_c2go.c` shims (names indicative), their
   wrappers, **the new by-value Vec3 API wrappers and parity tests
   (added as part of I-A)**, and the other 4.5.0 parity tests added by
   I-B/I-C/I-D/I-E. At the I-I cutover the `!h3v450` files are
   deleted, the default `H3VER` flips, and the tag machinery can be
   retired or kept for the next migration window.
3. **The h3ref oracle's source list becomes fresh-clone-safe and
   version-derived.** A bare `$(wildcard $(H3_LIB)/*.c)` is NOT
   suitable: `h3ref`'s prerequisite list contains `$(OBJECTS)`, so GNU
   make expands the wildcard while constructing the dependency graph —
   **before** the `h3-source` prerequisite has downloaded and
   extracted the tree — yielding an empty object list on a fresh
   checkout. Selected mechanism: drop the per-file object graph for
   the upstream sources and compile them at **recipe time**, after the
   `h3-source` prerequisite has completed, with a shell-expanded glob:
   `h3ref: h3-source h3ref.c` whose recipe runs
   `$(CC) $(CFLAGS) h3ref.c $(H3_LIB)/*.c -o h3ref $(LDFLAGS)` — the
   glob expands in the shell when the recipe executes, at which point
   the tree exists, and it is automatically correct for both versions
   (drops the deleted files at 4.5.0, picks up
   `area.c`/`cellsToMultiPoly.c`). Giving up incremental `.o` reuse is
   acceptable for a one-shot oracle build. (An equivalent alternative
   — a sub-`$(MAKE)` invoked after extraction so `$(wildcard)`
   re-evaluates in the child — is workable but adds a recursion layer;
   the recipe-time glob is the selected mechanism.)

   **`testref/h3ref.c` needs source-compatibility work of its own**
   (verified: the exact glob compile builds and runs at 4.4.0 but
   fails at 4.5.0 with "call to undeclared function `_geoToFaceIjk`"
   / "`_geoToHex2d`" — h3ref.c lines 223 and 237). Selected
   dual-version strategy: `testref/Makefile` derives a compile
   definition from `H3_VERSION` (e.g.
   `ifeq ($(H3_VERSION),4.4.0) CFLAGS += -DH3REF_HAVE_GEO_INTERMEDIATES endif`),
   and h3ref.c wraps the two command blocks and their two help lines
   (36–37) in `#ifdef H3REF_HAVE_GEO_INTERMEDIATES`. Selected
   behavior: the `geoToFaceIjk` and `geoToHex2d` commands are
   **retained only in the 4.4.0 oracle** and **retired in the 4.5.0
   oracle** (they fall through to the existing "Unknown command"
   error, exit 1) — the upstream intermediates no longer exist, their
   Go counterparts retire in I-A, and the 4.5.0 successors are not
   substitutable (`_vec3ToHex2d` is file-static in faceijk.c, so a
   drop-in replacement command cannot even link; the new pipeline is
   exercised end-to-end through the version-neutral `latLngToCell`
   command instead). The remaining 19 commands are version-neutral:
   the coordijk helpers resolve from the `static inline` header
   definitions at 4.5.0 in h3ref's own translation unit.
   `testref/README.md` (which documents h3ref and its example
   invocation) gains a note that these two commands exist only in a
   4.4.0-configured build.

Acceptance for I-T: `make test-c2go` (default, 4.4.0) stays green
unchanged; `make test-c2go H3VER=4.5.0` compiles and runs the subset of
parity tests valid for a not-yet-migrated port (everything except the
domains listed in §5 as changed), with the changed-domain tests
arriving issue by issue behind the `h3v450` tag. For the h3ref oracle,
acceptance is exercised **from a clean per-version testref state, and
each build is smoke-tested — source discovery alone is not
acceptance**. Each version cleans its own tree (`clean-all` uses
`H3_VERSION` to name the tree/archive it removes):

```sh
# 4.4.0: clean, download, build, smoke-test
make -C testref H3_VERSION=4.4.0 clean-all
make -C testref H3_VERSION=4.4.0
./testref/h3ref latLngToCell 37.775 -122.418 9      # prints the res-9 cell

./testref/h3ref latLngToCell 37.775 -122.418 9      # prints the res-9 cell
```

Both builds must succeed on a fresh checkout with no pre-existing
