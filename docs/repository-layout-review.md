# Repository layout review: public API layer vs mechanically ported layer

Status: **investigation complete; recommendation recorded as DR-008;
implementation phases 1–4 pending owner approval** (phase 0 — this document,
the `tools/layoutinventory` classifier, and `docs/file-layer-inventory.csv` —
lands together with this file).
Scope at time of writing: commit `5d189e7`, Go toolchain 1.26.5
(`go.mod` floor 1.24), parity target H3 C v4.4.0, 638 root source files
(620 `.go` + 18 `.c`).

This document investigates whether the repository should physically separate
its two logical layers — the idiomatic public Go API and the mechanically
ported H3 C implementation — into distinct packages (for example
`internal/h3`), and, if not, how to make the existing single-package layout
materially easier to understand. It is self-contained: a future maintainer
or coding agent should be able to execute the plan in §8 without access to
the conversation that produced it. Every load-bearing claim was verified
against the repository or by compile/benchmark probes reproduced in
[Appendix A](#appendix-a--probe-evidence).

Related records: [public-api-architecture.md](public-api-architecture.md)
(DR-001…DR-007, the original single-package decision),
[FUTURE_WORK.md](FUTURE_WORK.md) ("Intentionally rejected designs" and the
filename-convention cleanup item §12-Q12),
[lint-policy.md](lint-policy.md) (how ported files are matched),
[ci-policy.md](ci-policy.md) (which gates run when).

## 0. Executive summary

**The `internal/h3` split is not viable, and neither is any other package
split — this is a language-constraint conclusion, not a taste one.** The
type system forces the public index types, their methods, and the ported
algorithms that fill `[]Cell` buffers to live in one import-acyclic unit,
i.e. one package (§4). Every escape hatch sacrifices a locked invariant:

- Defining `Cell` in the root while the port lives in `internal/` makes
  `[]Cell` and the internal slice type **not even convertible** (P2); every
  hot path gains one allocation and a 3.4–4.6× boundary slowdown (P7),
  destroying the documented warm-path 0-alloc `Append*` guarantees.
- Moving everything into `internal/h3` and aliasing from the root
  (`type Cell = internal.Cell`) compiles and stays zero-copy (P4), **but the
  root package cannot attach methods to the alias** (P1), so the entire
  method-based API moves into the internal package: `go doc` and pkg.go.dev
  then show a bare `type Cell = h3.Cell` with **no visible methods** (P5),
  `reflect` `PkgPath` changes observably (P6) — and the two layers are *still
  physically mixed*, just one directory lower. The variant does not even
  solve the problem it exists for.
- A shared type package underneath both layers dead-ends in an import cycle
  the moment a method calls an algorithm (P3).

**Recommendation (DR-008): keep the single flat root package — reaffirming
DR-001 — and solve the real problem, discoverability, with a
machine-checkable layer inventory plus documentation.** Concretely:

1. `tools/layoutinventory` (committed with this document) classifies all
   638 root source files into nine layers from file evidence and emits
   [`docs/file-layer-inventory.csv`](file-layer-inventory.csv); `-verify`
   fails on any file that matches no layer rule, so the classification can
   never silently rot.
2. Phase 1 wires it into `make` and CI (freshness gate, same pattern as
   `docs/c-api-inventory.csv`).
3. Phase 2 upgrades the README repository map and CONTRIBUTING with a
   per-layer table and explicit "how to tell which layer a file is in"
   rules.
4. Phase 3 (optional) executes the pre-existing backlog item §12-Q12: rename
   the single casing outlier `h3Index_getBaseCellNumber.go`.

Nothing in the recommended plan touches production Go code, the public API,
the parity harness, or any allocation property; the proof obligation
(§10) is correspondingly trivial.

## 1. Problem statement

The root directory contains 620 Go files in one flat `package h3`. Two
logical layers coexist:

1. the **mechanically ported H3 C implementation** — one file per C
   function, C-shaped bodies, `// Ported from H3 C: <file>::<name>`
   attributions, unexported;
2. the **idiomatic public API** — typed `Cell`/`DirectedEdge`/`Vertex`
   values, methods, `Append*` zero-allocation forms, iterators, sentinel
   errors, exported.

The layers are logically crisp but physically interleaved: an alphabetical
listing shows `cell.go` between `bbox_types.go` and `constants.go`, and a
newcomer has no committed artifact that says which of the 638 files belongs
to which layer, or what the recognition rules are. The question under
investigation: is a package split the right fix, and if not, what is?

### 2.1 Which conventions are reliable, and which are not

Reliable today (and enforced as of phase 1 by `layoutinventory -verify`):

- **No-underscore basename ⇔ public API file.** Holds for all 16/16.
- **`<cmodule>` prefix ⇔ ported layer.** Holds for all 275 non-test and all
  271 module-prefixed test files.
- **`_parity_test` / `_cgo` / `h3lib_` ⇔ parity harness**, always paired
  with the `cgo && c2go` tag.

Not reliable, worth knowing:

- The `__` double-underscore convention ("C static helper") drifted long
  ago: 49 of the original 75 C-*public* functions live in `__` files
  (recorded as §12-Q12 in the architecture document). The sync tooling
  therefore keys on attribution comments, never on filenames.
- Upstream C *test* ports use two naming styles: bare `testGridDisk_test.go`
  and module-prefixed `baseCells_testBaseCells_test.go`. The case-level
  source of truth is `docs/upstream-test-inventory.csv`, not the filename.
- `h3api_types.go` and `polygon_types.go` look like ported support files but
  declare public types — they are the deliberate hybrid points where the
  two layers fuse (§3), now explicitly classified `ported-public-types`.
- `h3Index_getBaseCellNumber.go` is the lone casing outlier (uppercase `I`;
  every sibling uses `h3index`). Backlog item §12-Q12; optional phase 3.

## 3. How the two layers actually depend on each other

The dependency is **bidirectional at the type level**, which is the crux of
the whole investigation:

| Shared identifier | Declared in (layer) | Kind | Methods attached | Crosses the boundary as |
|---|---|---|---|---|
| `Cell` | `cell.go` (public) | defined `uint64` | ~60 public methods | `[]Cell` in every hot collection path |
| `h3Index` | `h3api_types.go` (hybrid) | **alias** `= Cell` | — | the ported layer's spelling of `Cell`; `[]h3Index` **is** `[]Cell` |
| `DirectedEdge`, `Vertex` | `edge.go`, `vertex.go` (public) | defined `uint64` | yes | scalars and `[6]h3Index` stack arrays only (≤6 elements, element-wise converted) |
| `Angle` | `angle.go` (public) | defined `float64` | yes | fields of `LatLng`/`bbox` used *inside* ported arithmetic (17 `.Rad()` sites) |
| `LatLng`, `GeoLoop`, `GeoPolygon`, `CellBoundary`, `CoordIJ` | `h3api_types.go` (hybrid) | defined | few | passed by pointer/value straight into ported algorithms; `GeoPolygon` with thousands of vertices enters `polygonToCells` with zero conversion |
| `ContainmentMode` | `polygon_types.go` (hybrid) | defined | `String` | flags word for the polyfill family |
| `h3Error` / `e*` codes | ported layer | defined | — | mapped to public sentinels by `toErr` (`errors.go`), array lookup, no allocation |
| iterator structs (`iterCellsChildren`, …) | ported layer | defined | — | wrapped by `iter.Seq` closures in `iter.go` |

Call direction: public wrappers call ~150 distinct ported functions;
ported code never calls public wrappers, but it **references public types
pervasively** (every `h3Index` parameter, every `LatLng` field access).
Within one package that reference is free; across packages it becomes an
import edge — see §4.

Module/import graph (arrows = imports; ✂ = separate `go.mod`):

```
cmd/h3 ──► internal/cli ──► h3 (root, flat package: both layers + parity harness)
                              ▲            ▲
        interop/uberdiff ✂ ───┘            │   (black-box, replace ../..)
        interop/uberbench ✂ ──────────────┘   (black-box, replace ../..)
        tools/* (8 command mains; read the tree, import nothing from h3)
        example_test.go (package h3_test — the only black-box test)
```

`cmd/h3`, `internal/cli`, and both interop modules consume **only the
exported API** (verified: no `unsafe`, no linkname, no export bridges
anywhere outside the root). Nothing outside the root references root Go
files by name; the only cross-tree file reference is
`interop/uberbench/mapping_test.go` reading `docs/comparison-uber-h3-go.csv`.

## 4. The language constraints, probed

All probes were run on Go 1.26.5 (P-numbers reference
[Appendix A](#appendix-a--probe-evidence); nothing below is inferred from
documentation alone).

**P1 — methods.** A package that aliases a type from another package cannot
declare methods on it: `cannot define new methods on non-local type Cell`.
Methods live where the type is defined, full stop.

**P2 — slices.** For distinct defined types `Cell` and `impl.H3Index`
(both `uint64`), `[]Cell` is neither assignable nor **convertible** to
`[]impl.H3Index` (Go spec, Conversions: slice element types must be
identical). The only bridges are an element-wise copy or `unsafe` —
prohibited in production by DR-007.

**P3 — cycles.** If the type + methods live in package *core* and the
algorithms in package *impl*, then *impl* must import *core* (its functions
take `[]core.Cell`) and *core* must import *impl* (its methods call the
algorithms): `import cycle not allowed`. The only acyclic resolutions are
(a) one package, or (b) methods+type+algorithms all together in one lower
package with a facade above — which is P4/P5.

**P4 — alias facade works mechanically.** `type Cell = internal.Cell` in
the root compiles; `[]Cell` is identical to the internal slice type
(aliases create *the same type*); forwarding functions inline. Zero-copy
survives this shape.

**P5 — but documentation does not.** `go doc` for the facade package shows
only `type Cell = impl.Cell` — **none of the ~60 methods** — and pkg.go.dev
does not render `internal/` packages at all, so the entire method surface
of the library becomes undiscoverable to users. For a library whose API is
predominantly methods on `Cell`, this is disqualifying on its own.

**P6 — reflection identity.** With the internal package also named `h3`,
`%T` and `reflect.Type.String()` remain `h3.Cell`, but `PkgPath()` changes
from `github.com/dimchansky/h3-go` to
`github.com/dimchansky/h3-go/internal/h3` — observable by anything keying
on the full path (gob registration, serializer registries). Since
`v0.1.0`/`v0.2.0` are published tags, this is now a real compatibility
consideration, unlike at DR-001 time when no releases existed.

**P7 — the copy tax, measured.** If the layers hold *distinct* index types
(the only split shape that keeps methods documented in the root), every
collection boundary pays an internal-typed temp allocation plus an
element-wise copy. Warm-path `Append*` calls go from 0 allocs to 1, and:

| n (result cells) | identity (today) | convert-copy boundary | ratio |
|---|---|---|---|
| 7 (k=1 disk) | 6.5 ns | 29.2 ns, 64 B | 4.5× |
| 19 (k=2 disk) | 8.6 ns | 41.2 ns, 160 B | 4.8× |
| 343 (children +3 res) | 121 ns | 501 ns, 3 072 B | 4.1× |
| 6 000 (polyfill-scale) | 1.92 µs | 7.02 µs, 49 152 B | 3.7× |

These numbers are the floor for the *boundary alone*, before any algorithm
work; they directly violate the README/doc.go allocation contracts and the
allocation-assertion tests.

**The consequence — the acyclic-unit rule.** Combining P1+P2+P3: the public
index types, their methods, and every ported algorithm that reads or writes
`[]Cell` must reside in a single package. The current root package is not a
style choice that a refactor can revisit; it is the only arrangement that
satisfies the locked invariants (methods on `Cell`, documented on
pkg.go.dev, zero-copy `[]Cell` pass-through, no `unsafe`).

## 5. Options evaluated

### Option A — keep the single package, improve the physical organization

What can actually be improved inside one package:

- a **generated, CI-gated per-file layer inventory** (the classifier and
  CSV shipped with this document) — turns the implicit conventions of §2.1
  into a machine-checked artifact;
- README/CONTRIBUTING upgrades stating the recognition rules;
- the §12-Q12 casing-outlier rename.

What cannot: Go forbids one package spanning multiple directories, and all
309 white-box tests, 19 cgo bridges, and 18 C shims (cgo compiles `.c`
files only from the package's own directory) are pinned to wherever the
package lives. A mass renaming of ported files to a grouping prefix (e.g.
`c_algos__gridDisk.go`) was considered and rejected: ~550 renames, churn in
`git blame`, both lint regexes, and the committed `c-api-inventory.csv`,
for a sort-order benefit the generated inventory provides better.

**Verdict: recommended, as "A+" — A plus the machine-checkable inventory
(details in §8).**

### Option B — move the mechanical port to `internal/h3`

Two shapes exist and both fail:

**B-alias** (everything — port, types, methods, wrappers — moves to
`internal/h3`; root becomes `type Cell = internal.Cell` aliases plus
forwarding functions). Mechanically sound (P4): zero-copy survives,
forwarders inline. Fails because: (a) the public method set disappears from
`go doc`/pkg.go.dev (P5) — disqualifying; (b) `PkgPath` breaks (P6);
(c) crucially, **it does not separate the layers**: the methods must stay
next to the ported code inside `internal/h3`, so the internal package is
exactly today's 620-file mix, one level deeper, with a ~40-file alias
facade on top; (d) migration churn is enormous and permanent: ~620 file
moves, `apiinventory` and `upstreamdiff` read the root non-recursively
(`tools/apiinventory/main.go:117,231`, `tools/upstreamdiff/main.go:274`)
and would report every function unported, both `.golangci.yml` exclusion
regexes are root-anchored, `make test-upstream-fixtures` (`Makefile:112`)
and the nightly fuzz-smoke job (`nightly.yml:60`) target the root package
`.`, and `apisurface_test.go` resolves `docs/api-surface.txt` relative to
the package directory.

**B-defined** (public types + methods stay in the root; `internal/h3`
gets its own index type). Kills zero-copy (P2, P7): warm 0-alloc `Append*`
becomes 1-alloc-plus-copy, wrapper tax 3.7–4.8×. Also every ported
signature must be rewritten away from the `h3Index` alias, destroying the
verbatim-body property that makes upstream diffs reviewable.

**Verdict: rejected. DR-001 reaffirmed with stronger evidence (published
tags now make P6 a real break; P5/P7 quantified).**

### Option C — shared representation package under both layers

`internal/h3core` owns `Cell` (+ methods), both root and `internal/h3impl`
import it. Dead on P3: methods in `h3core` call algorithms in `h3impl`,
which imports `h3core` — cycle. Escaping the cycle means moving the
algorithms into `h3core`, which recreates the single package under a new
name. **Rejected.**

### Option D — public types in a public (non-internal) subpackage

Same acyclic-unit trap as C: the subpackage that defines `Cell` must also
contain the methods and therefore the algorithms — i.e. the entire current
package moves to `h3-go/h3core` and the root becomes a facade. pkg.go.dev
would at least render the subpackage, but users then live with
`type Cell = h3core.Cell` indirection, split documentation, a changed
`PkgPath`, and a regenerated API-surface golden — real compatibility and
ergonomics cost, zero separation gained (the mix just changes directory).
**Rejected.**

### Option E — code generation / bridge layer

Generation cannot repeal P1 (method locality) or P2 (slice identity), so it
cannot enable any split the type system forbids; generated forwarders are
exactly Option B-alias with extra machinery. Generation for *verification*
(inventories) is already the repo's pattern and is what A+ extends.
**Rejected as a splitting mechanism.**

### Option F — partial extraction

Candidates examined one by one:

- **Parity tests + cgo bridges + C shims → `internal/c2go`** (would remove
  264 files from the root). The tests are white-box over ~250 unexported
  functions and internal types (`coordIJK`, `faceIJK`, …). Moving them
  requires a build-tagged export bridge in the root
  (`//go:build c2go`: `var C2GOGridDisk = gridDisk`, `type C2GOCoordIJK =
  coordIJK`, ×~250), rewriting all 227 parity files' call sites, and a
  permanent new maintenance step on every upstream sync. It also breaks the
  most useful traceability property the harness has: the
  `algos__gridDisk.go` / `algos__gridDisk_parity_test.go` *adjacent-pair*
  convention that makes function-scoped upstream review trivial. Cost far
  exceeds the benefit; the harness is already invisible to every normal
  build via `cgo && c2go`. **Rejected.**
- **C shims alone**: impossible without the above — cgo only compiles `.c`
  files located in the package directory; the shims must sit beside the
  bridges.
- **Lookup tables / generated fixtures / tooling**: tables are package code
  (must stay); tools, CLI, interop, and `testref` are already outside the
  root. Nothing movable remains.

**Verdict: nothing worth extracting; rejected.**

### Option G — discovered during the audit: make the layering machine-checkable

The audit's actual finding is that the two layers are *already* cleanly
distinguishable from file evidence (package clause, build tags,
attributions, exported declarations, filename shape) — reliably enough that
a ~230-line dependency-free tool classifies all 638 files with zero
ambiguity. What was missing was not structure but an **artifact**: a
committed, regenerable, CI-gated statement of the classification. That is
the recommendation, folded into A+ (§8).

## 7. Revisiting DR-001

DR-001 (single root package, two file layers) was decided pre-release, when
the package exported zero operations. Re-examination against today's state:

| DR-001 premise | Still true? | Notes |
|---|---|---|
| Methods must live with the defined type | **Yes** (P1) | unchanged through Go 1.26; generic aliases (1.24) do not affect method locality |
| `[]T` conversion requires identical element types | **Yes** (P2) | spec unchanged |
| Alias-to-internal hides method docs | **Yes** (P5) | re-verified with `go doc` on 1.26.5 |
| Parity tests are white-box and must stay in-package | **Yes** | 309/310 test files are `package h3` |
| No users, so compatibility is free | **No — changed** | tags `v0.1.0`/`v0.2.0` published; `PkgPath`/import-path stability now has beneficiaries, which *strengthens* DR-001 |
| Discoverability comes from filename conventions | **Partially** | conventions held but were never machine-checked or documented as recognition rules; §2.1 shows two of them drifted |

Conclusion: the original decision is not merely preserved but *reinforced*;
what changed is that the discoverability half of the bargain needs real
infrastructure instead of folklore. Recorded as:

**DR-008 — Layout: reaffirm the single flat root package; make the layer
classification a generated, CI-gated artifact.**
Context: 638 root files, two logical layers, newcomer discoverability
complaint; every package split fails P1–P7. Decision: no package moves; add
`tools/layoutinventory` + `docs/file-layer-inventory.csv` + a `-verify`
gate; document the recognition rules in README/CONTRIBUTING. Consequences:
production code, API surface, allocation properties, parity harness, and
sync workflow are untouched; the classifier becomes the tenth committed
inventory and must stay green like the others. Rejected: `internal/h3`
(both shapes), shared type package, public type subpackage, generated
bridges, parity-harness extraction — §5 and Appendix A/B.

## 8. Implementation plan (phased, for a coding agent)

Ground rules for every phase: run `make fmt lint test check-unsafe
check-docs`; the working tree must be releasable at each commit boundary;
each phase is one focused commit with the area prefix shown.

### Phase 0 — investigation record (this change) — `docs:` + `tools:`

Objective: land the decision record, classifier, and inventory.
Files: `docs/repository-layout-review.md` (this file),
`tools/layoutinventory/main.go`, `docs/file-layer-inventory.csv`
(generated), index rows in `docs/README.md` and `tools/README.md`.
Mechanical vs architectural: all additive; zero production-code changes.
Tests: `go vet ./tools/layoutinventory`, run with `-verify` (exit 0),
`make check-docs`.
Rollback: revert the commits; nothing depends on them.
Completion: CI `docs` job green; inventory CSV matches §2 counts.

### Phase 1 — wire the gate — `tools:` or `ci:`

Objective: make the classification self-maintaining.
Changes:

1. `Makefile`: add
   `layout-inventory` (`go run ./tools/layoutinventory > docs/file-layer-inventory.csv`)
   and `check-layout` (`go run ./tools/layoutinventory -verify >/dev/null`),
   both `.PHONY`.
2. `.github/workflows/ci.yml`: add `make check-layout` to the `fast` job
   (needs no `testref/`, runs in ~1 s) and a CSV freshness check to the
   `api-gates` job, mirroring the existing `c-api-inventory.csv` pattern:
   `make layout-inventory && git diff --exit-code docs/file-layer-inventory.csv`.
3. `docs/ci-policy.md`: one sentence documenting the new gate's tier.

Risks: a future file that matches no rule fails `check-layout` — that is
the feature; the error message lists the file, and the fix is either to
follow a convention or to extend the rules *deliberately* in
`tools/layoutinventory/main.go`.

## Appendix A — probe evidence

Probes were run 2026-07-13 on Go 1.26.5 (darwin/arm64) in a throwaway
module outside the repository; none of the probe code is committed (same
convention as public-api-architecture.md Appendix A). Each is reproducible
from the description.

**P1 — methods on a non-local alias.** Package `impl` defines
`type Cell uint64`; package `root` declares `type Cell = impl.Cell` and
attempts `func (c Cell) IsValid() bool`. Result:

```
cannot define new methods on non-local type Cell
```

**P2 — slice assignability/convertibility across defined types.** With
`type Cell uint64` (root) and `type H3Index uint64` (impl), passing
`[]Cell` where `[]impl.H3Index` is expected, and the explicit conversion
`[]implB.H3Index(out)`:

```
cannot use out (variable of type []Cell) as []implB.H3Index value in argument
cannot convert out (variable of type []Cell) to type []implB.H3Index
```

**P3 — shared-type-package import cycle.** `core` defines `Cell` with a
method calling `impl.GridDisk`; `impl.GridDisk` takes `[]core.Cell`:

```
package probe/cyc/core
        imports probe/cyc/impl from core.go
        imports probe/cyc/core from impl.go: import cycle not allowed
```

**P4 — alias facade compiles, zero-copy, inlines.** `internal/impl`
defines `Cell` + method + `GridDisk(origin Cell, out []Cell)`; root
declares `type Cell = impl.Cell` and
`func GridDisk(origin Cell, out []Cell) { impl.GridDisk(origin, out) }`.
Builds clean; `-gcflags='-m'` reports `can inline GridDisk`. `[]Cell` is
passed through with no conversion (alias ⇒ identical type, Go spec, Type
declarations).

**P5 — documentation of the facade.** `go doc ./aliasroot Cell` prints
only:

```
type Cell = impl.Cell
    Cell is an H3 cell index. (alias to internal type)
```

— no methods, although `impl.Cell` has them; `go doc -all` likewise. On
pkg.go.dev the target of the alias is an `internal/` package, which the
site does not render.

**P6 — reflection identity.** With the defining package `probe/internal/h3`
(package name `h3`) and alias in `rootlike`:

```
%T=h3.Cell  String=h3.Cell  PkgPath=probe/internal/h3
```

Today's baseline in this repository:

```
%T=h3.Cell  String=h3.Cell  PkgPath=github.com/dimchansky/h3-go
```

**P7 — copy-tax benchmark.** `//go:noinline` fill functions standing in
for `gridDisk`; "identity" fills `[]Cell` directly (today's alias design);
"convert-copy" allocates an internal-typed temp, fills it, copies
element-wise into `[]Cell` (the only legal bridge under B-defined,
caller-buffer reuse impossible without exposing the internal type).
`-benchtime 2000000x`, darwin/arm64:

```
BenchmarkIdentity_7        6.544 ns/op      0 B/op   0 allocs/op
BenchmarkConvertCopy_7    29.15  ns/op     64 B/op   1 allocs/op
BenchmarkIdentity_19       8.594 ns/op      0 B/op   0 allocs/op
BenchmarkConvertCopy_19   41.17  ns/op    160 B/op   1 allocs/op
BenchmarkIdentity_343    121.2   ns/op      0 B/op   0 allocs/op
BenchmarkConvertCopy_343 501.1   ns/op   3072 B/op   1 allocs/op
BenchmarkIdentity_6000  1919     ns/op      0 B/op   0 allocs/op
BenchmarkConvertCopy_6000 7022   ns/op  49152 B/op   1 allocs/op
```

**Spec references.** Conversions (slices convertible only with identical
element types); Type declarations (alias declarations denote *the same
type*); Method declarations (receiver base type must be defined in the
same package).
